# Mini NPU Simulator

## 개발 환경

- Python 3.10.4
- Python 3.8 이상 호환
- 외부 라이브러리 없이 표준 라이브러리만 사용
- 실행 명령: `python3 main.py`

## 개발 과정

1. 과제 지시 문서를 분석하여 필수 기능과 제출물을 확인했다.
2. Python 버전과 실행 경로를 확인했다.
3. Git 저장소를 생성하여 구현 과정을 단계별로 기록하기로 했다.
4. Cross 필터와 X 필터를 3×3 중첩 리스트로 표현했다.
5. 패턴과 필터의 같은 위치 값을 곱하고 누적하는 MAC 함수를 중첩 반복문으로 구현했다.
6. Cross 패턴을 기준으로 Cross 점수 5, X 점수 1이 계산되는지 assert로 검증했다.
7. `read_row()` 함수로 한 행의 입력을 실수 리스트로 변환했다.
8. 숫자 개수 불일치와 숫자 파싱 실패를 검사하고 올바른 입력까지 재입력받도록 구현했다.
9. `read_matrix()` 함수로 세 행을 입력받아 3×3 필터와 패턴을 구성했다.
10. 두 MAC 점수의 차이가 `1e-9`보다 작으면 판정 불가로 처리하는 epsilon 비교 정책을 적용했다.
11. 필터 A, 필터 B, 패턴 입력과 점수 출력을 `run_user_input_mode()` 함수로 분리했다.
12. 반복 메뉴를 구현하여 사용자가 종료를 선택할 때까지 사용자 입력 모드와 JSON 분석 모드를 계속 실행하도록 구성했다.
13. `data.json`의 필터와 패턴을 불러오고, 패턴 키에서 행렬 크기를 추출하여 같은 크기의 필터를 선택하도록 구현했다.
14. `+`, `cross`, `x` 레이블을 각각 `Cross`, `X`의 표준 이름으로 정규화했다.
15. 패턴과 Cross/X 필터가 예상한 N×N 크기인지 검사하고 크기가 잘못된 데이터는 FAIL로 처리했다.
16. 각 JSON 패턴의 Cross/X MAC 점수를 계산하고 epsilon 비교로 `Cross`, `X`, `UNDECIDED`를 판정했다.
17. 전체 PASS/FAIL 개수와 실패한 패턴의 예상값 및 실제 판정을 집계하도록 구현했다.
18. JSON 파일 누락, 문법 오류, 필수 구조 오류와 개별 패턴 데이터 오류가 발생해도 프로그램이 중단되지 않도록 처리했다.
19. `time.perf_counter()`로 MAC 연산만 1,000회 측정하고 한 번의 평균 실행 시간을 밀리초로 계산했다.
20. 3×3, 5×5, 13×13, 25×25 행렬의 성능을 측정하고 결과 요약 전에 출력하도록 구현했다.
21. 사용자 입력 모드에서 입력된 패턴과 필터 A/B의 MAC 연산을 각각 1,000회 측정하고 대표 평균 시간을 출력하도록 보완했다.
22. 크기별 성능 표에 N² 연산 횟수인 9, 25, 169, 625를 함께 출력하도록 보완했다.
23. 양의 홀수 N을 받아 가운데 행과 열을 1로 채운 N×N Cross 패턴을 자동 생성하도록 구현했다.
24. 두 대각선의 위치를 1로 채운 N×N X 패턴을 자동 생성하고 기존 3×3 필터와 일치하는지 검증했다.
25. 생성된 Cross/X 패턴을 성능 분석에 재사용하고, 패턴 자동 생성 모드를 메뉴에 추가했다.
26. N×N 2차원 행렬을 행 우선 순서의 길이 N²인 1차원 리스트로 변환하도록 구현했다.
27. 단일 인덱스로 순회하는 1차원 MAC을 구현하고 3×3, 5×5, 13×13, 25×25에서 기존 2차원 MAC과 점수가 일치하는지 검증했다.
28. 동일한 Cross/X 입력과 1,000회 반복 조건으로 2차원 및 1차원 MAC의 평균 시간을 비교하도록 구현했다.
29. 성능 측정을 10개 독립 세트로 구성하고, 각 세트에서 MAC을 1,000회 호출한 평균을 구한 뒤 10개 세트의 결과를 다시 평균하도록 보완했다.
30. 사용자 입력 모드와 JSON 분석 모드가 같은 epsilon 규칙을 사용하되 각각 `판정 불가`와 `UNDECIDED`로 표현하는 이유를 문서화했다.
31. 1000×1000 입력에서 예상되는 시간과 메모리 병목 및 블록·스트리밍 처리 방안을 분석했다.
32. CPU와 NPU의 MAC 처리 병목 차이와 NPU 오프로딩에 적합한 작업 범위를 정리했다.

## 실행 방법

프로젝트 디렉터리에서 다음 명령을 실행한다.

```bash
python3 main.py
```

사용자 입력 모드는 메뉴에서 `1`, JSON 분석 모드는 `2`, 패턴 자동 생성 모드는 `3`, 프로그램 종료는 `0`을 선택한다. JSON 분석 모드를 사용하려면 `data.json`을 `main.py`와 같은 디렉터리에 배치해야 한다.

## 동점 처리 정책

사용자 입력 모드와 JSON 분석 모드는 모두 두 점수의 차이가 `1e-9`보다 작으면 동점으로 보는 같은 epsilon 규칙을 사용한다. 사용자 입력 모드는 사용자가 직접 입력한 필터 A/B를 한국어 대화형 화면에서 비교하므로 동점을 `판정 불가`로 표현한다. JSON 분석 모드는 표준 라벨 `Cross`/`X`를 사용하는 일괄 분석 결과이므로 지시 문서의 출력 규칙에 맞춰 `UNDECIDED`로 표현한다. 즉 동점을 판단하는 계산 정책은 같고, 모드의 입력 이름과 출력 용도에 맞춰 표시 문자열만 다르다.

JSON의 `expected`는 `Cross` 또는 `X`로 정규화된다. 따라서 실제 판정이 `UNDECIDED`이면 expected와 일치하지 않으므로 해당 케이스는 FAIL로 집계된다.

## 보너스: 패턴 생성기

패턴 자동 생성 모드에서 양의 홀수 N을 입력하면 N×N Cross와 X 패턴을 출력한다. 정수가 아니거나 0 이하 또는 짝수인 크기는 오류 메시지를 출력하고 다시 입력받는다.

Cross 패턴은 가운데 행 또는 가운데 열인 위치를 1로 구성한다. X 패턴은 행 인덱스와 열 인덱스가 같거나 두 인덱스의 합이 `N - 1`인 위치를 1로 구성한다. 자동 생성한 패턴은 크기별 MAC 성능 분석에도 재사용한다.

## 보너스: 1차원 MAC 최적화

2차원 행렬을 첫 번째 행부터 차례로 이어 붙여 길이 N²인 1차원 리스트로 변환했다. 기존 MAC은 `matrix[row][column]` 형태로 접근하지만 1차원 MAC은 `matrix[index]` 형태의 단일 인덱스로 모든 원소를 순회한다.

성능을 비교하기 전에 두 구현의 MAC 점수가 일치하는지 검사했다. 3×3, 5×5, 13×13, 25×25 모두 같은 점수를 반환했다. 평탄화와 입출력 시간은 제외하고 같은 Cross/X 입력을 사용했다. 한 측정 세트에서 MAC 함수를 1,000회 호출해 1회 평균을 계산하고, 이 과정을 독립적으로 10회 수행한 뒤 10개 세트의 평균을 다시 구했다. 2차원과 1차원 방식에는 같은 측정 세트 수와 반복 횟수를 적용했다.

| 행렬 크기 | 2차원 평균 시간 | 1차원 평균 시간 | 측정상 빠른 방식 |
|---:|---:|---:|:---:|
| 3×3 | 0.000957 ms | 0.000535 ms | 1차원 |
| 5×5 | 0.002141 ms | 0.001276 ms | 1차원 |
| 13×13 | 0.011063 ms | 0.007099 ms | 1차원 |
| 25×25 | 0.037378 ms | 0.026700 ms | 1차원 |

측정에서는 네 크기 모두 1차원 방식이 더 빨랐다. 1차원 방식은 중첩 리스트의 행을 찾은 뒤 열을 조회하는 대신 하나의 리스트에서 연속적으로 값을 조회하므로 접근 구조가 단순하다. 다만 실행 시간은 운영체제와 CPU 상태에 따라 달라질 수 있으므로 특정 한 번의 측정값을 항상 재현할 수 있는 결과로 해석하지 않는다.

두 구현 모두 N²개의 값을 계산하므로 시간 복잡도는 `O(N²)`이다. 1차원으로 바꿔도 저장하는 원소 수는 N²이므로 입력 데이터의 공간 복잡도 역시 `O(N²)`이다. 평탄화 과정에서는 새 리스트 N²개 분량을 추가로 만들지만, 빅오 관점의 차수는 변하지 않는다. 따라서 이 최적화는 빅오 복잡도를 낮추는 것이 아니라 메모리 접근과 인덱스 구조를 단순화하는 최적화이다.

## 1000×1000 입력의 병목과 우선 최적화

N이 1,000이면 행렬 하나에 1,000,000개의 값이 있고, 패턴과 필터의 MAC 한 번에도 1,000,000개 위치를 계산해야 한다. 일반적인 64비트 환경에서 Python 리스트의 원소 참조만 고려해도 행렬 하나에 약 8 MB가 필요하며, 행 리스트와 숫자 객체의 오버헤드까지 포함하면 실제 사용량은 더 커진다. 패턴과 필터를 모두 저장하고 1차원 복사본까지 동시에 만들면 수백만 개의 참조가 중복되어 최대 메모리 사용량이 수십 MB 이상으로 증가할 수 있다.

25×25의 625개 연산과 비교하면 1000×1000의 1,000,000개 연산은 1,600배다. 이번 25×25 측정값을 N²에 비례한다고 단순 외삽하면 1000×1000 MAC 한 번은 약 60 ms, 1,000회는 약 60초, 10개 측정 세트는 약 10분이 걸릴 수 있다. 이는 실제 측정값이 아니라 현재 결과를 이용한 대략적인 추정이며, 캐시와 메모리 대역폭 및 시스템 상태에 따라 달라진다.

대형 입력에서는 먼저 2차원 원본과 1차원 복사본을 동시에 오래 보관하지 않고 필요한 표현 하나를 재사용해 중복 메모리를 줄여야 한다. 전체 행렬을 메모리에 올리기 어렵다면 행 또는 작은 블록 단위로 읽어 부분 점수를 누적하는 스트리밍 방식을 적용할 수 있다. Cross/X처럼 값 1의 위치가 적은 필터라면 1인 위치의 인덱스만 저장하는 희소 표현도 고려할 수 있다. 이러한 방법으로도 시간이 부족할 때 병렬 처리나 전용 가속기로 MAC 계산을 옮기는 순서가 적절하다.

## CPU와 NPU의 병목 차이

CPU도 여러 코어와 벡터 명령을 지원하지만, 현재 Python 구현은 인터프리터에서 중첩 반복문을 순차 실행하므로 반복문 해석 비용과 인덱스 조회 및 메모리 접근이 주요 병목이 된다. 반면 NPU는 많은 MAC 연산 장치를 병렬로 배치하고 입력과 가중치를 내부 메모리에서 재사용하도록 설계되어 크고 규칙적인 행렬·텐서 계산에 유리하다.

NPU로 옮기기 적합한 부분은 JSON 읽기나 사용자 입력 및 라벨 정규화가 아니라 `calculate_mac()`의 위치별 곱셈·누적 연산이다. 3×3처럼 작은 작업 하나만 전송하면 데이터 이동과 장치 호출 비용이 계산 시간보다 클 수 있다. 큰 행렬, 많은 필터 또는 여러 패턴을 묶어 처리하고 데이터를 가능한 한 NPU에 유지할 때 병렬 처리 효과가 커진다. 따라서 설계할 때는 MAC 커널을 큰 단위로 묶어 오프로딩하고 CPU는 입력 검증, 실행 흐름 제어, 결과 집계를 담당하도록 역할을 나누는 것이 적절하다.

## JSON 분석 결과

총 6개의 패턴을 분석한 결과 PASS 3개, FAIL 3개가 나왔다.

- `size_5_1`: expected=X, actual=UNDECIDED
- `size_13_2`: expected=Cross, actual=UNDECIDED
- `size_25_1`: expected=X, actual=UNDECIDED

세 실패 사례는 Cross 점수와 X 점수의 차이가 epsilon 값인 `1e-9`보다 작아 `UNDECIDED`로 판정됐기 때문에 발생했다. 부동소수점 계산에서는 수학적으로 같은 값도 매우 작은 오차를 가질 수 있으므로 직접 동등 비교하지 않고 epsilon 비교를 적용했다.

## 성능 분석 결과

각 크기에서 테스트 패턴과 필터를 생성한 뒤, 입출력과 행렬 생성 시간을 제외하고 MAC 함수 호출 구간만 측정했다. 한 측정 세트에서 MAC을 1,000회 반복한 1회 평균을 구하고, 독립적인 측정 세트 10개의 결과를 다시 평균했다.

| 행렬 크기 | 평균 실행 시간 | 연산 횟수(N²) |
|---:|---:|---:|
| 3×3 | 0.000955 ms | 9 |
| 5×5 | 0.002125 ms | 25 |
| 13×13 | 0.011235 ms | 169 |
| 25×25 | 0.037831 ms | 625 |

실행 시간은 컴퓨터 상태에 따라 달라질 수 있지만 행렬 크기가 커질수록 전반적으로 증가했다.

`calculate_mac()`은 N개의 행과 각 행의 N개 열을 중첩 반복문으로 순회하므로 총 N²개의 위치를 계산한다. 따라서 시간 복잡도는 `O(N²)`이다. 입력 행렬을 제외하고 누적 점수와 반복 인덱스만 사용하므로 MAC 연산 자체의 추가 공간 복잡도는 `O(1)`이다.
